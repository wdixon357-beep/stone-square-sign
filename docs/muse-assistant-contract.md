# Muse Assistant access and attestation queue

Service and client contract. Deployment and installed-version receipts establish which revision is live.

## Boundaries

The assistant is a separate service identity bound to the active Worshipful Master, never a Lodge officer/member/user or an owner session. It cannot retrieve the separate stored signature image, generate an owner session or assertion, or change its own grants. The owner may separately enable instructed execution and supported exact-document signatures. Those operations identify Muse as the executor under saved owner delegation. Protected signed PDFs remain readable under existing record permissions. Unknown routes are denied. Existing officer, ownership, source, financial, generation, consent and signature rules remain in force. No additional paid service is required by the design; existing generation limits remain enforced.

The catalog covers this service's existing named permissions and owner-only workflows, including routes guarded directly by owner role rather than a named capability. Base modes are standing (granted reads/previews), approval (exact non-signature change), personal (an existing owner workflow), and unavailable (another office or unsupported integration). Owner-controlled `commandExecution` allows granted approval actions to run after a specific instruction relayed by Muse. Separately, `signatureExecution` allows five supported personal actions through the exact-document signature engine. The base catalog mode does not override those explicit settings. Personal applies to implicit signatures such as Building Approve, not only buttons named Sign. Imported text cannot authorize work. An instruction relayed by Muse is recorded as delegation, never as independently authenticated chat consent or proof that the owner reviewed a document.

## Shared JSON endpoints

All responses are private/no-store. Human owner endpoints retain normal authenticated same-origin checks. Assistant access uses a separately issued bearer token; only a hash is stored. Revocation/expiry are checked on every request.

- GET /api/assistant/workspace -> { assistant: null | {id,name,enabled,expiresAt,permissions,commandExecution,signatureExecution,createdAt,updatedAt}, capabilities:[{id,label,group,mode,description,effects:[]}], requests:[], attestations:[], activity:[] }. Owner only. GET /api/assistant/me returns the assistant identity, permitted action catalog and integration instructions for the assistant token.
- PUT /api/assistant/access {name,permissions:[actionId],expiresInDays,enabled,commandExecution?,signatureExecution?} -> {assistant}. Owner only. Days 1..365, default7. Saving a longer duration preserves the existing token; token rotation remains a separate action. Both delegation settings default to false and preserve their saved values when omitted. They do not permit direct personal business endpoints; supported signatures use their dedicated instruction endpoint.
- POST /api/assistant/access/token -> {assistant,token}. Owner only. Token displayed once. Rotation immediately invalidates the previous token. No automatic issuance just by opening a page.
- DELETE /api/assistant/access -> {ok:true}. Owner only, immediately revokes.
- GET /api/assistant/requests -> {requests}; GET /api/assistant/requests/:id -> {request}. Owner or that assistant, never other officers. Requests include {id,actionId,title,method,path,body,status,fingerprint,createdAt,expiresAt,decidedAt,decisionNote,effects:[],navigation:{section,recordId}|null,receipt:null|object}.
- POST /api/assistant/requests {actionId,method,path,body,requestKey,title?} -> {request}. Validate action/method/path, bound JSON size and fields, resolve actual record/office authority and current fingerprint server-side. A stable requestKey deduplicates one exact proposal and rejects changed payload reuse. Generic personal requests only queue a review. Signature requests use the separate frozen-document engine.
- POST /api/assistant/requests/:id/decision {decision:'approve'|'decline',fingerprint,note?} -> {request}. Human owner only. Changed, expired or revoked requests cannot be approved. Personal-mode requests show Open review, not Approve/Execute; the human uses the existing signing workflow with current checks. Non-signature approval is exact/single-use/short-lived and checked against the unchanged record before execution.
- GET /api/assistant/attestations -> {attestations}. Owner's pending personal work and relevant assistant requests. Each {id,kind,recordId,title,status,section,actionLabel,attestationText,effects:[],revision,requestId?,ready,reason?}. Show actual source/preparer/review limitations. No inference of completed confirmations. Includes owner minutes Master/preparer stages, assigned dispensation signatures, own treasury attestation, building approvals/filing and any other owner signature-bearing action discovered by registry.

## Clients

Both clients add Muse Assistant and My Attestations navigation for the owner. The access screen groups every action, explains its mode, saves allowed preparation/action scopes, issues/revokes a token deliberately, and shows recent assistant activity/requests. My Attestations shows the exact document/action and all effects, opening the existing record-specific review screen. It never submits a signature on mount, navigation, refresh, assistant command or generated confirmation. With signature delegation off, signature execution requires owner confirmation. With it on, an explicit instruction for the exact frozen document can be executed by Muse and is labeled accordingly.

The web client uses existing api/fetch/session/error behavior and responsive workspace styles. The Mac client uses native SwiftUI navigation, tables/cards/sheets and the existing service connection, without rendering the web interface. Copy/text must say what is actually supported. Token creation is configuration, not proof Muse connected. A live integration is verified only by a successful assistant read; testing uses isolated synthetic data only.

## Audit and receipts

Persist assistant identity and authorizing owner separately. Existing audit inserts must preserve the executing actor in addition to the owner, including modules which insert directly. Record each assistant request and its outcome. Mutating assistant requests require a stable idempotency key; an uncertain execution must never be automatically repeated. A signature receipt records the owner whose signature was applied, the requester, and whether execution followed owner confirmation or a relayed instruction under delegation. Preserve all signed snapshots, signatures, source and prior audit history.

Approval consumption and the legacy business transaction are separate. The durable execution entry is consumed once. Existing revision checks and additional locked checkpoints reject stale writes inside the business transaction. A crash or ambiguous response leaves an execution requiring verification, with no automatic retry. This does not promise a distributed transaction across notifications, the portal or other services.

## Connection and current limits

The connector exposes JSON Streamable HTTP at POST `/api/assistant/mcp`. It supports `workspace`, `read`, `read_file`, `request_action`, `request_upload`, `authorize_instruction`, `requests`, `execute`, `request_signature`, `sign_instruction` and `signature_status`. It uses the separate bearer credential and fixed loopback forwarding. There is no arbitrary network destination, owner assertion, private invitation link or reusable signature image. `request_upload` computes metadata and SHA256 from the supplied base64 bytes; `execute` verifies and sends the identical files, preserving names, order and form fields. Transfers allow up to twelve files and 30,000,000 total decoded bytes. A 42 MiB JSON envelope is restricted to authenticated assistant connections. `read_file` returns permitted complete documents up to 30,000,000 bytes.

After a separately approved release, the owner can save access, deliberately create a token, and configure a compatible Muse connector with the service URL plus `/api/assistant/mcp`. Opening either client does not issue a token. A token receipt does not establish that Muse supports this authentication method or has connected. Actual Muse connection remains unverified until its authenticated read succeeds. No new provider or subscription is needed by this implementation.

Building details use a verified, read-only PostgreSQL projection with signature, credential and payment fields omitted. Creating a Building request remains a personal portal submission because the portal accepts human sessions. A returned submission reference alone is retained as unverified and does not close the queued request. Candidate Tracker's existing owner assertion is unavailable to the assistant until that external service supports a separately attributed identity. These limits are visible in the action catalog.

Treasury preparation preserves source names and extraction evidence exactly. Existing personal review flags can survive only when their associated facts are unchanged. Muse cannot create a personal confirmation, forge field reviews, or change a source-matched financial value while leaving it marked as supported. The actual preparer completes those corrections and reviews in the existing screen.

Creating a dispensation and approving a Warden proposal apply the saved Master signature, so both are personal actions. Muse can render an explicitly unsigned dispensation preview. Generic personal requests open the existing review tools. A supported exact-document signature request can instead use the owner-enabled signature instruction route. A personal completion receipt must match the prior record version and any proposed preparation, or, for a new dispensation, the exact preparation plus the actual document, human signing row and creation audit. Unmatched work remains unresolved.

The code and verification in this checkout are local. No production schema, account permission, credential, Lodge record, installed application, deployment, billing setting or monitoring schedule is changed by building and testing it.

## Exact-document signature confirmation

William may instruct Muse to apply his saved signature to a specific document. Muse first freezes a request. With `signatureExecution` off, the authenticated owner opens the link and selects **Authorize and apply signature**. With it on, Muse may call `sign_instruction` with the exact request fingerprint and the specific instruction. The system applies the signature through the same checked operation. Receipts distinguish owner confirmation from execution by Muse under saved delegation. Neither a session nor a relayed instruction proves physical presence or personal review.

- POST `/api/assistant/signature-requests` accepts an assistant-only `{actionId,method,path,body,requestKey}`. It freezes the eligible saved document's review PDF and binds the record state, statement, effects, owner, signature profile, assistant policy/token versions, implementation identity and expiry. A changed payload cannot reuse the request key. Muse cannot supply personal review flags or a signature image.
- GET `/api/assistant/signature-requests` and GET `/:id` provide requests and receipts to the owner or originating assistant. GET `/:id/preview` is owner-only and serves the frozen PDF. The trusted HTTPS `/?signatureRequest=<id>` link carries an identifier, not authority. Normal browser login may be needed; native authentication is not copied into Muse or the browser.
- POST `/:id/confirm` is authenticated-owner-only and requires `{fingerprint,consent:true}`. It rechecks the unchanged record and authority, then commits the existing business signature, authorization consumption and audit together. Delivery runs after that commit. A GET, preview, status read or client navigation never signs. The separate instruction endpoint below can sign only under the owner's saved delegation.
- POST `/:id/decline` is owner-only. Expired, revoked, changed or already consumed requests cannot be applied again. After an interrupted response, clients read the receipt instead of retrying a signing write. An unresolved processing or uncertain result remains blocked pending verification.

Supported operations are Master and actual-preparer minutes attestations, the owner's own assigned treasury preparation, pending document signatures assigned to the owner, and creation of an official dispensation with the Master's signature. The new-dispensation confirmation lists the exact entered facts and both Secretary assignments; its saved receipt identifies the actual created document. It never supplies a Secretary signature or sends to the District Deputy. Preparation, attendance, source, financial and other officers' confirmation requirements remain enforced. Warden proposal decisions and external Building or Report Generator signing remain outside this contract until their complete document, authority, statements and delivery effects can be bound safely. This limit must be visible to Muse and the owner; it is not full impersonation of William.

New signature requests share the existing 30-per-minute and 100-pending queue bounds. Their frozen PDFs also have a 64 MiB retained total per assistant across all states. Matching live requests are rejected before a second PDF is rendered; original-key retries return the existing status. Completed or expired history is not automatically deleted to make room. Oversized or nested creation fields are rejected before storage. Reaching capacity directs the owner to the existing personal workflow.


## Instructed execution

- `POST /api/assistant/requests/:id/instruction` accepts only the originating assistant and `{fingerprint,instruction,instructionReference?}`. The owner must have enabled `commandExecution`. The current grant, payload, record, policy version and expiry are checked. The request becomes `authorized`, distinct from human `approved`. `execute` consumes either state once and returns a bounded receipt including available record identifiers.
- `POST /api/assistant/signature-requests/:id/instruction` accepts the same instruction fields and requires `signatureExecution`. Owner identity, assignment, actual preparer, frozen artifact, signature profile, implementation, token, policy and record are rechecked before claiming and applying. It cannot supply missing personal review flags or another officer's signature.
- Instruction text is required, limited to 2,000 characters, with an optional 300-character message reference. It is retained as `relayed_by_assistant` with an explicit false flag for independent human verification. It is not a new authenticated chat channel.
- Both controls are owner-only and off by default. Changing policy invalidates earlier pending work. Revocation, token rotation, expiry, changed documents and uncertain outcomes keep their existing protections. The owner may decline an instruction-authorized request before execution.
- Muse's allowlist excludes the legacy Missive retry action. Frozen signature operations retain the signed document and packet for Spark follow-through without creating a Missive draft. Ordinary signing outside this integration still has legacy email behavior and requires separate migration. This release does not add a Spark send tool.
